# Обоснование событийного подхода vs Camel/DWH

## Проблемы текущей интеграции (Camel ESB + DWH)

1. **Централизованная бизнес-логика в DWH.** Значительная часть логики зашита в SQL Server 2008: любое изменение затрагивает всех, замедляет time-to-market.
2. **Точечные синхронные интеграции через Camel.** Жёсткая связность: недоступность одного сервиса каскадом ломает цепочку. Рост числа интеграций даёт квадратичную сложность (N×N).
3. **Batch-отчётность.** Сотни ТБ, множество трансформаций → отчёты строятс часами, нет near-real-time.
4. **Плохая масштабируемость по направлениям.** Добавление домена (фарма, электроника) требует новых сложных интеграций и правок в общем DWH.
5. **Единая точка отказа и узкое место.** DWH и шина общие для всех доменов.

## Что даёт переход на события

| Критерий | Camel ESB + DWH (as-is) | Событийная платформа (to-be) |
|----------|-------------------------|------------------------------|
| Связность | Сильная (синхронные вызовы) | Слабая (асинхронные события) |
| Отказоустойчивость | Каскадные сбои | Изоляция сбоев, DLQ, повторы |
| Масштабирование | Вертикальное, дорого | Горизонтальное (партиции Kafka) |
| Скорость реакции | Batch, часы | Near-real-time, секунды |
| Добавление домена | Правки в DWH/шину | Подписка на топик, новый consumer |
| Владение данными | Централизованное | Доменное (Data Mesh) |
| Time-to-market | Низкий | Высокий |

### 1. Гибкость и слабая связность
Издатель события не знает о подписчиках. Новый домен (фарма, электроника) подключается, просто подписавшись на нужные топики без изменения источника и без правок в DWH. Это устраняет N×N-сложность интеграций.

### 2. Масштабируемость
Kafka масштабируется горизонтально через партиционирование. Рост числа источников и событий (одна из целей 3 лет) обрабатывается добавлением партиций/консьюмеров, а не апгрейдом монолитного DWH.

### 3. Скорость реакции (near-real-time)
Потоковая обработка (Kafka Streams/Flink) материализует витрины по мере поступления событий. Переход от batch к near-real-time прямая цель бизнеса. Антифрод, уведомления, оперативные метрики работают в реальном времени.

### 4. Независимая эволюция и владение данными
Каждый домен владеет своими событиями и дата-продуктами (Data Mesh). Контракты фиксируются в Schema Registry с контролем совместимости домены, развиваются независимо, не ломая потребителей.

### 5. Надёжность
- **Outbox pattern** - гарантированная публикация событий вместе с изменением агрегата.
- **DLQ** - ошибочные сообщения не блокируют поток.
- **Event replay** - переигрывание истории событий для восстановления/новых витрин.

## Роль legacy на переходный период

Camel и DWH не выключаются одномоментно, а работают как **мосты совместимости**
через **Anti-Corruption Layer**:
- Debezium/CDC вычитывает изменения из DWH и публикует нормализованные события.
- Camel-интеграции оборачиваются ACL и постепенно замещаются событиями (strangler-паттерн).
- К этапу 3 (18–36 мес) синхронные интеграции на критическом пути выводятся.

## Вывод

Событийный подход напрямую закрывает боли «Будущего 2.0»: ускоряет time-to-market, снимает нагрузку с DWH, обеспечивает near-real-time аналитику и позволяет масштабировать бизнес по продуктам, географии и данным без роста интеграционной сложности. Это фундамент целевой слабосвязанной событийной платформы.
